# Fix plan — 19 reported issues, 2026-08-22

No code changed. Each item below was traced to a specific line before a fix was
proposed; where I could not determine intent from the code, it is listed under
**Decisions needed** rather than guessed at.

Three of the reports turned out to describe something slightly different from
what is actually wrong. Those are marked **Correction** and are worth reading
first, because they change what the fix should be.

---

## Corrections to the reports

### Standard reports events are already audited — except exports

`src/actions/report-templates.ts` already writes audit rows for template
**create** (`:141`), **update** (`:262`) and **delete** (`:339`). Nothing is
missing there.

What is genuinely unaudited is **export**. "Export CSV" and "Generate PDF"
(`standard-reports-preview-panel.tsx:154,163`) run entirely in the browser from
data already on the client, so no server code observes them and there is nothing
to log from. Fixing this needs a deliberate server round trip, not a call added
to an existing action — see item 19.

### The repair dialog does not "record the currency incorrectly" — it discards it

`log-complete-repair-dialog.tsx:105` renders
`<Select defaultValue="LKR">` with **no `value`, no `onValueChange`**, and the
currency is not part of `formData`. Only `actualCost` is submitted. The picker
is decorative: whatever you choose, the number is stored bare.

And there is nowhere to put it — `maintenance_tickets` has `estimated_cost` and
`actual_cost` but **no currency column**. So this is a schema gap, not a
form-wiring slip. See item 10.

### The acknowledgement reminder sends the return-request notification verbatim

Not "similar to" — identical. `triggerAssignmentReminders`
(`operations-assignments-repo.ts:968`) dispatches:

```ts
eventType: 'RETURN_REQUESTED',
title: 'Return Reminder',
message: `Reminder: IT has requested the immediate return of ${asset}.`
```

That is the button shown on **pending acknowledgement** rows. Someone who has
not yet accepted an assignment is told to return it. See item 3.

## A. Assignment lifecycle

### 1. Acknowledgement vs return reminders are the same notification

**Root cause** `triggerAssignmentReminders` reuses `RETURN_REQUESTED`
(`:968`). The correct event, `ASSIGNMENT_PENDING`, already exists in the
`notification_event_type` enum and already has a rule row and a display name
("Pending Asset Assignment").

**Fix** Split into two paths that already have distinct events:

| Trigger                                                   | Event                | Wording                                |
| --------------------------------------------------------- | -------------------- | -------------------------------------- |
| Send Reminder on a `pending approval` row                 | `ASSIGNMENT_PENDING` | "…is waiting for your acknowledgement" |
| Request Return / Send Reminder on `assigned` or `overdue` | `RETURN_REQUESTED`   | existing wording                       |

The email side needs the same split: `sendAssetNotification({ type:
'assignment_reminder' })` is one template used for both.

**Files** `operations-assignments-repo.ts` (`triggerAssignmentReminders`,
`triggerReturnRequests`), `src/lib/notifications/*` for the email template.
**Effort** S · **Risk** Low — additive, both events already exist.

### 2. Pending status not visible on the grid or detail pages

**Root cause** The registry grid's Status column shows `assets.status`, which is
`Assigned` the moment an assignment is created — the assignment's own `state`
(`pending approval`) is never surfaced outside the operations grid.

**Fix** Show both, as separate signals: asset status stays as-is, and a second
badge appears when an open assignment is not yet acknowledged. `StatusBadge`
already has a `pending_approval` entry with the "Pending assignment" label.
Requires `asset-registry-repo` to carry the open assignment's `state` on the row
(it already joins assignments for `assignedTo`).

**Files** `asset-registry-repo.ts`, `use-asset-columns.tsx`,
`asset-details-panel.tsx`. **Effort** M · **Risk** Low.

### 3. Operations panel: "Assigned to" blank for electronics, and Department should go

**Root cause** Two separate things, both confirmed:

- `operations-assignments-repo.ts:451,520` map `assignedTo: row.assignedToUser
|| null` — the dashboard query resolves the **user** only. A location
  assignment has none, so the field is blank. This is the same defect already
  fixed on the asset-registry detail path, on a second code path that was
  missed.
- `asset-assignment-panel.tsx:220` renders a Department row that falls back to
  `props.group`, and `use-assignments-dashboard.ts:44` hardcodes several of
  these fields to `'-'` anyway.

**Fix** Join `locations` in the dashboard query and fall back to it, exactly as
`asset-details-repo` now does; label the row "Location" for location-assigned
pillars via the existing `isLocationAssignedPillar`. Remove the Department row.

**Files** `operations-assignments-repo.ts`, `use-assignments-dashboard.ts`,
`asset-assignment-panel.tsx`. **Effort** S · **Risk** Low.

### 4. Operations tab should offer Transfer once assigned

**Root cause** The repo now supports reassignment (`ASSIGNABLE_STATUSES` plus
`closeOpenAssignments`), but the operations panel still only offers **Assign**,
so the capability is unreachable from that screen.

**Fix** For location-assigned pillars with an open assignment, label the action
**Transfer** and open the same modal pre-filled with the current location. No
server change — the transfer path already exists and is tested.

**Files** `asset-assignment-panel.tsx`, `assignments-panels.tsx`.
**Effort** S · **Risk** Low.

### 5. Merge the two asset-panel workflows — **the largest item**

**Root cause** Two implementations of the same panel have drifted:

|         | Registry path                             | Operations path               |
| ------- | ----------------------------------------- | ----------------------------- |
| Wrapper | `asset-details-panel-wrapper.tsx`         | `assignments-panels.tsx`      |
| Panel   | `asset-details-panel.tsx`                 | `asset-assignment-panel.tsx`  |
| Data    | `getAssetDetailsByIdAction` (full record) | dashboard row + partial fetch |

The registry path has the correct workflows; the operations path carries older
logic but also fields the registry path lacks. The evidence that they drift is
already on record: the missing `imageUrl` prop, the hardcoded `'-'` fields, and
the location bug in item 3 all existed on one path only.

**Fix — staged, not one commit:**

1. Make the operations path load through `getAssetDetailsByIdAction`, so both
   read the same shape. Behaviour unchanged, differences become visible.
2. Move the fields only the operations panel has (reminder/return/receive
   actions, assignment metadata) into the registry panel behind a `mode` prop.
3. Delete `asset-assignment-panel.tsx`; point `assignments-panels.tsx` at the
   registry panel.

**Effort** L · **Risk** **Medium — the highest of anything here.** Do it on its
own branch, after the small items, and lean on the existing
`asset-assignment-panel.test.tsx` and `asset-details-panel.test.tsx`.

### 6. Post-return check should preview the resulting status

**Root cause** The mapping exists server-side only
(`operations-assignments-repo.ts:1377-1391`):

| Condition                   | Resulting status |
| --------------------------- | ---------------- |
| Good Working Condition      | Available        |
| Minor Issues / Needs Repair | In Repair        |
| Beyond Repair               | Pending Disposal |

`process-return-modal.tsx` never shows it, so the outcome is a surprise.

**Fix** Extract the mapping into a shared pure function (e.g.
`src/lib/assignments/return-outcome.ts`), have the server switch call it, and
render "This asset will move to **In Repair**" live in the modal. Sharing it is
the point — a duplicated copy would drift, which is the pattern behind items 3
and 5.

**Files** new shared module, `operations-assignments-repo.ts`,
`process-return-modal.tsx`. **Effort** S · **Risk** Low.

## B. Software licences

### 7. Expired licences still show seats as available

**Root cause** The availability column (`use-asset-columns.tsx:227-265`)
computes seats only and never reads `expiryDate`, so an expired licence with
free seats reads "8 / 10 Available". The row already carries `expiryDate`, and
`asset-registry-repo.ts:306,523` already derives `isExpired` for the status
column.

**Fix** Gate the badge on expiry first: expired → a single **Unavailable**
badge; otherwise the existing seat count. Reuse the `isExpired` the repo already
computes rather than recomputing it in the column.

**Files** `asset-registry-repo.ts` (expose `isExpired` on the row),
`use-asset-columns.tsx`. **Effort** S · **Risk** Low.

### 8. No way to renew an expired licence

**Root cause** Not a bug — the capability does not exist. `software_licenses`
has `expiryDate`, but no action updates it after registration.

**Fix** A `renewSoftwareLicenseAction` taking a new expiry date, guarded by
`canManageAssets`, writing an audit row, and a **Renew** button on the licence
detail panel shown when expired or near expiry. Reuse the date presets from
`assignment-date-utils` (6 months / 1 / 2 / 5 years / custom) so renewal terms
match the rest of the app.

**Decision needed:** should renewing also restore seats, or only extend the
date? See Decisions.

**Files** new action, `asset-details-panel.tsx`, validation schema.
**Effort** M · **Risk** Low.

## C. Maintenance

### 9. Warranty shown as a status, not a date

**Root cause** `issue-review-panel.tsx:126` renders `warrantyStatus` — the

**Files** `src/actions/maintenance.ts` (add `warrantyExpiry` to the returned
shape), `issue-review-panel.tsx`. **Effort** S · **Risk** Low.

### 10. Repair completion discards the currency — and has nowhere to store it

**Root cause** See the Correction above: the Select is unwired, and
`maintenance_tickets` has no currency column.

**Fix, in order:**

1. **Migration** adding `currency_code varchar(3)` to `maintenance_tickets`,
   defaulting to `'LKR'` to match `asset_purchases.currency_code`. Follow the
   established pattern: `ADD COLUMN IF NOT EXISTS`, non-destructive, and the
   drift test will check it.
2. Control the Select — `value` + `onValueChange`, currency in `formData`, and
   in the validation schema.
3. Persist and display it: `formatMoneyByCurrency` already exists and is used
   by the audit log formatter.
4. Backfill is not needed; existing rows take the default.

**Note:** the same gap probably affects `estimated_cost` in
`initiate-repair-dialog.tsx` — worth checking while in there.

**Files** new migration, `schema.ts`, `log-complete-repair-dialog.tsx`,
`actions/maintenance.ts`, validation schema. **Effort** M · **Risk** Low.

### 11. Repair log dialog UI/UX

## D. Financials and reports

### 12. Financials pages are bare tables

Design work. All three (`/financials/depreciation`, `/salvage`, `/tco`) are a
heading plus a grid. Proposed, in value order:

1. **A summary row** above each table — total book value, accumulated
   depreciation, count of fully depreciated assets. The data is already loaded.
2. **Depreciation:** a chart of book value over time; per-row remaining life as
   a progress bar rather than a number.
3. **TCO:** purchase vs maintenance cost as a stacked bar per asset, which is
   the comparison the page exists to support.
4. **Salvage:** group by disposal outcome, and show realised vs expected
   salvage.
5. An "as of <month>" note — depreciation steps in whole calendar months, so a
   figure that does not move between visits currently looks stale.

**Effort** L · **Risk** Low (additive). **Decision needed:** which of the four.

### 13. Financials filters

**Root cause** The three ledgers have search and pagination but no filtering by
the fields that matter: category, pillar, location, purchase-date range, or
depreciation state (active / fully depreciated / disposed).

**Fix** Reuse `src/components/shared/filter-bar.tsx`, which already backs the
registry and operations grids, rather than building a third filter UI. Push the
filters into `getDepreciationLedger` / `getTCOLedger` / `getWriteOffsLedger`
rather than filtering client-side — these tables page server-side, so
client-side filtering would silently filter only the current page.

**Effort** M · **Risk** Low.

### 14. Preview with no filters errors instead of being disabled

**Root cause** `handleManualPreview` (`standard-reports-shell.tsx:91`) sets
`showDataGrid(true)` with no validation. With no data source chosen, the
downstream fetch has nothing to query and throws.

**Fix** Two layers:

- Disable **Preview report** until a data source is selected, with a tooltip
  saying why. Cheap and stops the error.
- Return a typed "no data source" result from the action instead of throwing, so
  a direct call cannot produce an unhandled error either.

**Files** `standard-reports-config-panel.tsx`, `standard-reports-shell.tsx`,
`actions/standard-reports.ts`. **Effort** S · **Risk** Low.

### 15. PDF generation blocked by CSP — **fix this first**

**Root cause** Certain. The production CSP in `next.config.ts:13` is:

```
script-src 'self' 'unsafe-inline'
```

`@react-pdf/renderer` lays out with Yoga compiled to **WebAssembly**, and
`WebAssembly.instantiate` requires `'wasm-unsafe-eval'` (or the much broader
`'unsafe-eval'`). Development sets `'unsafe-eval'` (`:14`), which is exactly why
this only appears in production.

**Fix** Add `'wasm-unsafe-eval'` to the production `script-src`. It permits
WebAssembly compilation **only** — it does not re-enable `eval()` — so it is far
narrower than `'unsafe-eval'` and does not undo the SEC-G work.

Apply it in **both** policies or the report-only one will fire false violations:

- `next.config.ts:13` — enforced policy
- `src/proxy.ts:168` — report-only nonce policy

**Also affects asset tag printing**, which uses the same renderer — so this is
almost certainly broken in production too, just not yet reported.

**Files** `next.config.ts`, `src/proxy.ts`. **Effort** XS · **Risk** Low.

### 16. Audit log export covers only the current page

**Root cause** `audit-log-client.tsx:464` calls `downloadCsv(rows)`, where
`rows` is the current page.

**Fix** Ask, as the reports panel already does for its CSV export: a small
dialog offering **Current page (N rows)** or **All matching records (M rows)**.
`getAllAssetAuditHistory` shows the pattern for an unpaginated fetch; the
all-records path needs a server action honouring the active filters, with a cap
(say 10,000) and a clear message when exceeded.

**Files** `audit-log-client.tsx`, `actions/audit-log.ts`.
**Effort** M · **Risk** Low — but note the all-records path must not load an
unbounded result set into memory.

### 17. Report exports are not audited

**Root cause** Export runs entirely client-side (see Correction), so no server
code sees it.

**Fix** Add a `logReportExportAction(templateId | dataSource, format, rowCount)`
called just before the download starts. `AuditActionType` needs a new member —
`REPORT_EXPORTED` — and `lib/audit-events.ts` a phrase for it so it renders in
the feed and timeline like every other action.

**Effort** S · **Risk** Low.

## E. UI consistency

### 18. Role badge in the profile menu

**Root cause** `top-header.tsx:280` is a bespoke `Badge` with hardcoded
`#7cc000`, `text-[10px] font-bold uppercase tracking-wider px-1.5 py-0` — it
predates the badge unification and is now the last one outside it.

**Fix** Render `<StatusBadge variant="metadata" label={roleLabel} />`, which
picks up the shared `BADGE_LAYOUT`. If roles should stay visually distinct,
add role keys to `BADGE_DICTIONARY` rather than reintroducing inline styles.

**Files** `top-header.tsx`. **Effort** XS · **Risk** Low.

### 19. My Assets card UI

Design work. The cards (`src/components/shared/asset-card.tsx`) currently show
icon, name and tag. Proposed:

- The **assignment state** badge — an employee cannot currently tell an
  acknowledged asset from one still awaiting their acceptance, which is exactly
  what the Accept/Decline prompt above is about.
- **Expected return date**, with an overdue treatment — the one date that
  matters to the holder.
- The model image, with the existing icon as fallback (`models.imageUrl`, the
  same field the maintenance panel was reading from the wrong table).
- Move Accept/Decline onto the card itself rather than a separate alerts block,
  so the action sits with the asset it concerns.

**Effort** M · **Risk** Low.
